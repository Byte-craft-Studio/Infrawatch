This record captures the six decisions the team accepted for version 1 of InfraWatch. Any change to these decisions must be proposed as a new record that references this one. Do not edit this file to change a decision after it has been accepted.

## 1. Classification, not detection

The on-device model classifies each photo into one label: pothole, broken light, water leak, or other. It does not draw boxes around damage or estimate size.

Reasoning: classification is lighter to run on a phone and easier to label, and one label is enough to route a report to the right department. Severity in version 1 comes from the citizen's description, how many people confirm the report, and how long it has been open. Detection (for example YOLO) is a later option if classification proves too coarse.

Licensing note: the Ultralytics YOLO models are AGPL-3.0. Choosing MobileNetV2 avoids that question for version 1.

## 2. Separate public and private copies of each report

Exact coordinates live only in the `reports_private` collection, which only verified officials can read. A second document, in `reports_public`, holds the location offset by about 50 metres. The offset is randomised once per report, so repeated reports cannot be averaged to recover the exact position. The public map reads only `reports_public`. Security rules block public reads of `reports_private`.

Reasoning: the privacy guarantee comes from the data never reaching the public side, not from a filter in an endpoint that could have a bug.

## 3. Officials are approved manually through a named process

Official access is granted only to accounts that a designated administrator at the county or ward office has verified, using a government email domain or written confirmation from the office. Access is set through Firebase custom claims. Every grant and revocation is written to the `audit_log` collection.

Reasoning: an access system that is not tied to a real office cannot be trusted by citizens. For the pilot, one or two people at one office is enough.

## 4. Citizen confirmation before a report closes

An official can mark a report as fixed, but it moves to "pending confirmation" until a set number of nearby users confirm the fix, or until a set period passes without dispute. A dispute reopens the report and notifies the office.

Reasoning: this is what makes the public record more trustworthy than the office's own word. The fields for confirmation are added to the data model now, even though the full flow is built in Weeks 4 to 6.

## 5. Version 1 scope

Included: citizen report flow (photo, GPS, category, optional description, anonymous or signed-in), official status changes with timestamps, the public map, and confirmation.

Reserved in the data model but not built: ward grouping (a single field now), deadlines, and escalation.

Reasoning: each additional feature adds work before the core loop has been tested with real reports.

## 6. Face blurring on the server for version 1

Photos are uploaded to the backend, faces are blurred there, and the original is deleted immediately after. Users are told that the original is briefly uploaded. On-device blurring is the goal for a later version.

Reasoning: on-device blurring is the stronger privacy choice, but it is the hardest part to build in React Native and could delay the whole project.
